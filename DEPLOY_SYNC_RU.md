# Интеграция бота и miniapp: выкладка с сохранением данных

Текущий рабочий бот — единственный владелец `stats.json`. Miniapp больше не читает отдельную копию прав на другом диске: публичный API проксирует запросы в API внутри того же процесса бота. История обучения остаётся в существующей SQLite API-сервиса; бот обращается к ней по защищённому внутреннему RPC.

## Что сохраняется

- Существующие пользователи, имена, usernames, подписки, платежи, рефералы и произвольные поля JSON.
- Старые агрегаты гистологии и рейтинги анатомии: новые результаты добавляются при чтении общей статистики, старые агрегаты не заменяются.
- Существующие таблицы SQLite. Добавляются новые таблицы попыток анатомии и ключей повторных запросов гистологии; нет DROP, DELETE, ALTER или переноса базы.
- Исходные Railway volumes и пути `STATS_DIR`. `/data` у бота и API — разные диски, объединять/перемонтировать их нельзя.

Перед включением owner создаётся проверенная копия исходного JSON с правами 0600 в `sync_backups` на том же диске. Перед готовностью gateway SQLite проверяется `quick_check`, затем копируется через SQLite backup API, включая WAL; копия проверяется. Отсутствующий/повреждённый файл не заменяется пустой базой. Эти механизмы проверены на синтетических данных; наличие и целостность production-копий пока не подтверждены. Локальная копия на том же volume не заменяет независимый резервный архив.

Оставить один экземпляр бота. Для общего секрета `BOT_SYNC_TOKEN` сгенерировать новый случайный секрет и передать обоим сервисам через Railway variables; не сохранять в Git или отчёты. Существующий `SESSION_SECRET` API сохранить, в боте использовать ссылку `${{vmeda-miniapp-api-preview.SESSION_SECRET}}`. `BOT_TOKEN`, `STATS_DIR`, `MINIAPP_URL`, ключи AI, режим допуска miniapp и allowed origins сохранить. В боте использовать ссылки на существующие `MINIAPP_ACCESS_MODE` и `WEB_API_ALLOWED_ORIGINS` API.

Дополнения боту:

```
BOT_SYNC_MODE=owner
BOT_SYNC_HOST=::
BOT_SYNC_PORT=8081
REQUIRE_EXISTING_STATS=1
LEARNING_BACKEND_URL=http://vmeda-miniapp-api-preview.railway.internal:8080
```

Дополнения API:

```
BOT_SYNC_MODE=gateway
BOT_SYNC_URL=http://vmeda-biology-bot.railway.internal:8081
PORT=8080
SYNC_REQUIRE_EXISTING_DB=1
```

Старт API: `uvicorn web_api.main:app --host :: --port $PORT`. Удалить из start command старое создание пустого `stats.json`; исходный файл сохранить. Healthcheck API `/healthz` подтверждает готовность локального журнала; доступность owner дополнительно проверять через авторизованный `/api/v1/sync/state`. В production не запускать тестовые fixture-модули.

## Порядок и ограничения

1. Проверить точные HEAD веток, CI, текущие сервисы, volumes и единственный poller. Подготовить параметры без немедленного деплоя (`skipDeploys=true`).
2. Выложить gateway с существующим SQLite и проверить SUCCESS/healthcheck. До старта owner пользовательские API-запросы вернут 503; локального обходного чтения прав нет.
3. Выложить бот с owner на том же volume. Проверить единственный poller, создание проверенной копии JSON, отсутствие Telegram Conflict и доступность приватного API. Не менять/удалять volume и не запускать второго poller. Файловый lock защищает от второго владельца на том же volume, но не от ошибочно созданного второго volume.
4. Обновить frontend и проверить из Telegram подписку, ограничения, прогресс, избранное, повторный ответ, рейтинги и истёкшую сессию.
5. При ошибке вернуть предыдущий код/конфигурацию на тех же volumes, сохранив новые таблицы и данные. Не восстанавливать старую копию поверх актуальной базы автоматически. Если старый код не умеет читать новую историю, временно закрыть соответствующий интерфейс, сохранив записи.

Railway автоматически деплоит main для бота и feature/vmeda-mini-app для API/frontend. Merge этих веток без подготовленной конфигурации запускает выкладку. Замена процесса бота с подключённым volume требует технического перезапуска. Поэтому буквальный запрет любого перерыва несовместим с включением owner в уже работающий процесс; до разрешения этого противоречия production rollout не выполнять.

## Проверки и пределы

Команды: `python tests/run_all.py`, `python -m pytest web_api/tests -q`, `ruff check .`, `python sync_tests/check_sync.py`, `python sync_tests/check_services.py`, в miniapp `npm ci && npm run build && npm run lint`. Все тестовые токены фиктивны; данные — отдельные временные каталоги. Браузерная проверка: после сборки и установки Playwright `VMEDA_BROWSER_SMOKE=1 python sync_tests/check_services.py`.

Общее состояние прав обновляется в miniapp при возвращении/восстановлении сети и каждые 15 секунд видимой вкладки; сервер всегда проверяет актуальные права. Новые результаты гистологии и анатомии записываются в общий журнал с защитой от повторов; незавершённые части не попадают в рейтинг. Прогресс и избранное физиологии учитывают оба интерфейса, сохраняя прежнюю историю карточек.

Исторические AI-счётчики в отдельном прежнем JSON API не объединяются вслепую с JSON бота: файл сохраняется. Прошлые ответы анатомии, которые старый бот не записывал, восстановить невозможно. Текущая сессия нативного интерфейса бота остаётся в памяти; записанные ответы сохраняются, но экран сессии после перезапуска не восстанавливается автоматически. Эти ограничения не позволяют назвать полную историческую синхронизацию подтверждённой до production-аудита.
