# VMEDA web_api — read-only backend (Этап 3 ТЗ)

Отдельный процесс от `telegram_bot.py`. Сегодня — только проверка Telegram `initData` и один
реальный эндпоинт (`GET /api/v1/me`), читающий состояние через **те же самые** функции доступа,
которыми пользуется сам бот (`services/access.py`, реэкспортированные на `telegram_bot`), а не
переизобретённые заново.

## Важное архитектурное ограничение

`services/access.py` сам делает `import telegram_bot as tb` — значит, чтобы честно посчитать
доступ (`has_free_access`, рефералы, подписку), `web_api` вынужден импортировать **весь**
`telegram_bot.py`: конструктор `aiogram.Bot(token=BOT_TOKEN)` (падает без валидного токена),
`Dispatcher`, все хендлеры, все JSON-базы контента. См. подробный разбор в `web_api/bot_state.py`.
Практически это значит:

- `web_api` нужен **тот же `BOT_TOKEN`**, что и боту (не два разных бота).
- Импорт занимает заметное время (секунды — загрузка контента) один раз при старте процесса.
- `telegram_bot.stats` — это словарь в памяти конкретного процесса. Если бот (другой процесс)
  что-то записал в `stats.json` после старта `web_api`, копия устаревает молча — на КАЖДЫЙ
  read-only запрос, которому нужны свежие данные, эндпоинт обязан объявить
  `Depends(get_fresh_bot_module)` (см. `deps.py`), который перечитывает файл заново.
- `web_api` **ничего не пишет** в `stats.json` — сегодня это read-only слой (Этап 3 ТЗ). Как
  только появится реальная запись (избранное, прогресс), два процесса, пишущих в один JSON-файл
  без транзакций, станут реальным риском гонки — см. Этап 4 (PostgreSQL) в ТЗ, это не решается
  здесь.

## Запуск

```bash
pip install -r web_api/requirements.txt
export BOT_TOKEN=...          # тот же токен, что у бота
export SESSION_SECRET=...     # свой секрет, только для web_api (подписывает session-токены)
uvicorn web_api.main:app --reload
```

Запускать из корня репозитория — как и бот, `web_api` полагается на относительные пути к
JSON-контенту (`repositories/knowledge.py`).

## Тесты

```bash
python3 -m pytest web_api/tests/          # ВСЕГДА с явным путём — см. ниже, почему
```

**Не запускай голый `pytest` из корня репозитория** — `tests/` (тесты бота) не написаны под
pytest: это отдельные скрипты с `asyncio.run(main())` на верхнем уровне модуля (см. корневой
`CLAUDE.md`), и pytest, пытаясь их импортировать по маске `test_*.py`, выполнит их код как побочный
эффект импорта, а не как pytest-тесты. Запускай тесты бота его собственным раннером
(`python3 tests/run_all.py`), тесты `web_api` — только с путём `web_api/tests/`.

`web_api/tests/test_auth.py` и `test_session.py` — чистые unit-тесты (подпись `initData`,
session-токены), telegram_bot.py не импортируют вообще. `test_integration.py` — единственный
файл, который реально импортирует `telegram_bot` (через ленивый `bot_state.get_bot_module()`) —
сам выставляет `BOT_TOKEN`/`STATS_DIR`/`SESSION_SECRET` в изолированную временную директорию до
первого запроса, реальный `stats.json` репозитория не трогает.

## Что дальше

Эндпоинтов пока два (`POST /api/v1/auth/telegram`, `GET /api/v1/me`) — они существуют, чтобы
доказать всю цепочку целиком (проверенная `initData` → сессия → реальное решение о доступе), а
не покрыть весь список из ТЗ §4 разом. Следующие эндпоинты добавляются тем же паттерном: новый
файл в `routers/`, `Depends(get_current_user_id)` + `Depends(get_fresh_bot_module)`, чтение через
уже существующие функции `tb.*`, не новая логика.
