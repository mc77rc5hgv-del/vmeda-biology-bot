# VMEDA web_api — backend Mini App

Отдельный процесс от `telegram_bot.py`. Проверяет Telegram `initData`, выдаёт короткоживущую
серверную сессию и читает профиль, подписку, права доступа и учебный контент через **те же самые**
функции и данные, которыми пользуется бот, а не переизобретённые клиентом правила.

## Важное архитектурное ограничение

`services/access.py` сам делает `import telegram_bot as tb` — значит, чтобы честно посчитать
доступ (`has_free_access`, рефералы, подписку), `web_api` вынужден импортировать **весь**
`telegram_bot.py`: конструктор `aiogram.Bot(token=BOT_TOKEN)` (падает без валидного токена),
`Dispatcher`, все хендлеры, все JSON-базы контента. См. подробный разбор в `web_api/bot_state.py`.
Практически это значит:

- `web_api` нужен **тот же `BOT_TOKEN`**, что и боту (не два разных бота).
- Импорт занимает заметное время (секунды — загрузка контента) один раз при старте процесса.
- `telegram_bot.stats` — это словарь в памяти конкретного процесса. Если бот (другой процесс)
  что-то записал в `stats.json` после старта `web_api`, копия устаревает молча — на КАЖДЫЙ
  read-only запрос, которому нужны свежие данные, эндпоинт обязан объявить
  `Depends(get_fresh_bot_module)` (см. `deps.py`), который перечитывает файл заново.
- `web_api` **ничего не пишет** в `stats.json`. Прогресс, избранное и попытки тестов Mini App
  сохраняются в отдельной транзакционной базе `miniapp_learning.sqlite3` в `STATS_DIR`. Поэтому
  пользовательские данные бота, подписки и платежи не затрагиваются. В Railway `STATS_DIR`
  должен находиться на persistent volume.

## Запуск

```bash
pip install -r web_api/requirements.txt
export BOT_TOKEN=...          # тот же токен, что у бота
export SESSION_SECRET=...     # свой секрет, только для web_api (подписывает session-токены)
export STATS_DIR=...          # тот же persistent volume, где бот хранит stats.json
export MINIAPP_ACCESS_MODE=admin_only  # закрытая beta; public — открыть всем пользователям
uvicorn web_api.main:app --reload
```

Запускать из корня репозитория — как и бот, `web_api` полагается на относительные пути к
JSON-контенту (`repositories/knowledge.py`).

## Тесты

```bash
python3 -m pytest web_api/tests/          # ВСЕГДА с явным путём — см. ниже, почему
```

**Не запускай голый `pytest` из корня репозитория** — `tests/` (тесты бота) не написаны под
pytest: это отдельные скрипты с `asyncio.run(main())` на верхнем уровне модуля (см. корневой
`CLAUDE.md`), и pytest, пытаясь их импортировать по маске `test_*.py`, выполнит их код как побочный
эффект импорта, а не как pytest-тесты. Запускай тесты бота его собственным раннером
(`python3 tests/run_all.py`), тесты `web_api` — только с путём `web_api/tests/`.

`web_api/tests/test_auth.py` и `test_session.py` — чистые unit-тесты (подпись `initData`,
session-токены), telegram_bot.py не импортируют вообще. `test_integration.py` — единственный
файл, который реально импортирует `telegram_bot` (через ленивый `bot_state.get_bot_module()`) —
сам выставляет `BOT_TOKEN`/`STATS_DIR`/`SESSION_SECRET` в изолированную временную директорию до
первого запроса, реальный `stats.json` репозитория не трогает.

## Контент-адаптер (`content.py`) — что уже покрыто

`content.py` переводит реальную структуру "динамических" предметов (`generated_courses/*.json`,
т.е. `telegram_bot.DYNAMIC_COURSES` — сегодня это Биохимия/Фармакология/Латынь/Правоведение) в
JSON контентного контракта ТЗ §14. **Статичные предметы** (Физика/Химия/Биология/Анатомия/
Гистология/Оперативная хирургия) имеют собственные схемы. `static_content.py` уже покрывает
Нормальную физиологию: 23 темы курса и 11 рубежных контролей, разбитых на 127 удобных страниц,
включая 46 защищённо отдаваемых изображений. Остальные 6 предметов пока не подключены.

Реальная структура курса честно отражена, а не сплющена: раздел бывает **плоским** (список
уроков напрямую, большинство разделов Биохимии/Латыни/Правоведения) или **с группами**
(единственный сегодня пример — раздел "Курс" Фармакологии, 6 групп, ~1200 уроков) — эндпоинт
`GET /api/v1/subjects/{id}/sections/{id}` возвращает `kind: "flat"|"grouped"` и разную форму тела
в зависимости от того, что реально в данных. `GET /api/v1/materials/{subject}/{section}/{item}`
работает одинаково для обоих случаев — не нужно знать заранее группу урока (проверено на реальных
данных: id урока уникален в пределах раздела даже у Фармакологии — 1174 из 1174).

Медиа (`GET /api/v1/materials/.../media/{index}`) отдаётся `FileResponse`, путь к файлу берётся
ТОЛЬКО из уже найденного урока (`content.get_material()`), клиент передаёт лишь индекс — не сырой
путь. `show_sources: false` у предмета (сегодня — только Фармакология) вычищает `sources` из
ответа API, ровно как это уже делает `handlers/dynamic_courses.py` для самого бота.

Эндпоинты сегодня: `POST /api/v1/auth/telegram`, `GET /api/v1/me`,
`GET /api/v1/subscription`, `GET /api/v1/access/{subject_id}`, `GET /api/v1/subjects`,
`GET /api/v1/subjects/{id}`, `GET /api/v1/subjects/{id}/sections/{id}`,
`GET /api/v1/subjects/{id}/sections/{id}/groups/{id}`,
`GET /api/v1/materials/{subject}/{section}/{item}` (+ `/media/{index}`),
`GET /api/v1/learning/state` и команды изученного/избранного. `web_api/tests/test_content.py`
проверяет `content.py` на маленькой ручной фикстуре (без импорта бота);
`web_api/tests/test_subjects_integration.py` гоняет тот же путь через настоящий HTTP-запрос на
реальных файлах Биохимии, Фармакологии и Физиологии — включая изображения, отданные через
защищённый `/media/`.
