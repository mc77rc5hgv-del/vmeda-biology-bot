# Подготовка codeePay

Структура добавлена отдельно от работающей оплаты Telegram Stars. Модули не импортируют
`telegram_bot`, не создают HTTP-клиент, не открывают базы и не регистрируют публичные маршруты.
Никакие существующие пользователи, подписки, квитанции и статистика не изменяются.

## Что подготовлено

- `contracts.py`: серверный заказ с ценой в целых минимальных единицах валюты, идемпотентный
  ключ, результат создания счёта, внутренние статусы и контракт платёжного провайдера.
- `config.py`: выключенные по умолчанию настройки; ключи исключены из repr. HTTPS-адрес и
  таймаут проверяются до будущего сетевого вызова.
- `providers/codeepay.py`: отдельный адаптер для создания счёта, запроса статуса и проверки
  webhook. Пока все операции завершаются `ProviderNotReady`, даже если включён флаг и заданы
  ключи. Названия HTTP-методов, пути, формат авторизации и подписей не выдумываются.
- `validate_confirmation`: проверка подтверждённого платежа по сохранённому заказу —
  провайдер, номер заказа/платежа, статус, сумма и валюта. Она не выдаёт подписку.

## План подключения после получения документации

1. Реализовать авторизацию, создание/поиск счёта, статусы, подтверждение и проверку подписи
   webhook по фактическому API; протестировать в sandbox провайдера.
2. Добавить отдельный журнал заказов/событий в новом billing-хранилище на существующем
   persistent volume. Не использовать существующие таблицы учебной базы и не переписывать
   `stats.json` ради регистрации неоплаченного заказа. Уникальные ключи: внутренний заказ,
   provider/payment ID и provider/event ID; исходная цена фиксируется сервером.
3. Настроить отдельный webhook-маршрут: он сначала проверяет подпись на исходных байтах и
   ответ провайдера, затем надёжно регистрирует событие. Продумать доступ к нему через
   существующие gateway/owner guards; не открывать внутренние API или состояние бота.
4. Добавить серверный checkout из действующих тарифов бота. Клиент передаёт только тариф и
   допустимый предмет; сумму, валюту и пользователя определяет сервер. Возврат с оплаты
   или клиентское `paid` не являются подтверждением.
5. Только процесс существующего бота применяет подтверждённый платёж. Повторный callback
   не продлевает подписку дважды; сохраняются квитанция и исходная подписка. Смена тарифа
   проверяется текущим `purchase_reason`, сохраняет срок, права и AI-счётчики. Между журналом
   заказа и выдачей доступа нужна возобновляемая обработка после сбоя; простого флага `paid`
   в двух независимых файлах недостаточно.
6. Подключить интерфейс и обновление общей подписки после серверного подтверждения.
   Действующая оплата Stars остаётся доступна. До включения внешнего checkout проверить
   ограничения Telegram для покупки цифрового доступа в miniapp и согласовать применимый
   канал codeePay (например, отдельный сайт), исходя из текущих правил платформы.

## Переменные окружения (предварительные)

`CODEEPAY_ENABLED=false`, `CODEEPAY_API_URL`, `CODEEPAY_API_KEY`,
`CODEEPAY_WEBHOOK_SECRET`, `CODEEPAY_MERCHANT_ID`, `CODEEPAY_TIMEOUT_SECONDS=15`.
После получения документации состав и обязательность реквизитов уточняются: например,
проверка webhook может требовать публичного ключа вместо общего секрета. Реальные ключи
добавляются в секреты окружения, не в репозиторий, frontend bundle или логи.

Нужны документация API (включая webhook, подпись, статусы, валюты/единицы суммы, повторы,
возвраты и идемпотентность), sandbox-реквизиты и разрешённые callback/return URL. Успешная
настройка переменных сама по себе ещё не включает внешнюю оплату.
